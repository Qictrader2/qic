### Why deferring 1 + 2 is safe

The on-chain runs were architected to be doctrinally compliant with
the design doc (`devnet via the public faucet`). Both
`api.devnet.solana.com requestAirdrop` and the `solana airdrop` CLI
returned rate-limit / "Internal error" responses across multiple
attempts on 2026-05-08, against multiple wallets and IPs. This is a
known industry issue (the public Solana faucet has been chronically
overloaded since the 2024 memecoin spike) — not a project-specific
problem.

Two options were considered for unblocking:

- **Web faucet (`faucet.solana.com`)** — requires interactive human
  action (browser, captcha). Wallet `47cJKZ2jsPDToF4gfBqxhKLuQwYs1eMiFfrF4B8hGnxC`
  was generated for this path and remains funded-on-demand.
- **Switch to local validator** — rejected because it deviates from
  the design doc and the failure modes it would catch (signature
  format, ATA derivation, instruction encoding) are already caught
  by the deterministic offline checks 3 + 4.

The deferral is to TKT-214.3 (Helius RPC migration) because:

1. Helius's RPC bundles devnet airdrops with no per-IP throttling for
   paid plans, which the project will be on for production anyway.
2. Once TKT-214.3 lands, checks 1 + 2 reduce to a one-liner against
   the Helius devnet endpoint with the project's API key — repeatable
   from CI, no human in the loop.
3. The `cargo test … --ignored check_1 check_2` invocation is
   already wired up; only the RPC URL needs to switch from
   `https://api.devnet.solana.com` to the Helius equivalent. A
   commented-out branch in the test (`DEVNET_RPC` const) makes this
   trivial.

### What the offline checks already prove

The risk the design doc was hedging against in §6 is _"the existing
754 lines were assumed correct; what if they aren't?"_. Each of the
suspected failure modes has a code-level analogue that **is** covered
by the offline checks:

| Suspected failure mode (devnet check) | Equivalent offline guarantee | Check |
|---|---|---|
| ATA derivation diverges from Solana's reference impl | Compared against `spl-token-cli 5.5.0` oracle on 5 vectors | 3 |
| Encrypted keypair can't be recovered to sign | 3 round-trips through v0, v1, v0→v1 migration | 4 |
| Decimal conversion off by a power of ten | 9 dp / 6 dp pinned against mainnet `getTokenSupply` | 5 |
| Code is scaffolding the author would push back on | Author identified (JP), commit history shows intentional design + post-incident hardening | 6 |
| Signature math wrong (sig fails verification) | `sign_and_serialize_produces_valid_bytes` unit test in `solana.rs` re-verifies signatures it produces | inline tests |

What the offline checks **cannot** prove and what therefore strictly
remains in TKT-214.3's scope:

- The actual public devnet RPC accepts our wire-format
  (`api.devnet.solana.com` semantically agrees with `agave-validator`'s
  `processTransaction`).
- Real-network confirmation timing matches our `confirm_solana_tx`
  polling assumptions (30 attempts × 2 sec = 60 sec budget).

Both are operationally low-risk: the devnet RPC runs the same
`agave-validator` binary as mainnet, and the confirmation polling is
already exercised against a `wiremock` server in `solana.rs`'s inline
tests with both success and failure responses.

The verification harness lives in
`qictrader-backend-rs/tests/tkt_214_1_solana_devnet_verify.rs`. Checks 1 + 2

mint (cached at `${KP%.json}.mint`). Only the per-run receiver wallet rotates.

## Check 3 — ATA derivation matches `spl-token-cli` oracle

**Status:** **PASS** — 5/5 vectors match.

The codebase has its own `get_associated_token_address` implementation
that bypasses `solana-sdk` (`solana.rs` lines 100–106 calling
`find_program_address` at line 80). The risk is that this hand-rolled
implementation diverges from the official `spl-token-cli` for some edge
case, which would corrupt every Solana SPL deposit address we generate.

The verification compares 5 `(owner, mint) → ATA` triples against the
output of `spl-token --verbose --owner $OWNER --token $MINT address`
(spl-token-cli 5.5.0). All 5 match exactly. The vectors are pinned in
`tests/tkt_214_1_solana_devnet_verify.rs::ATA_VECTORS` so any future
regression breaks loudly.

The follow-up assertion `check_3_followup_ata_is_not_on_curve` confirms
that derived ATAs are not valid ed25519 points, which is a structural
invariant the SPL Token Program relies on.

**Implication:** the existing `get_associated_token_address` is correct;
TKT-214.2's "add `USDT_SPL_MINT` constant" is sufficient. No change to
ATA derivation needed.

## Check 4 — Encrypted Solana keypair round-trips through `wallet_crypto`

**Status:** **PASS** — 3/3 round-trips.

Three round-trips are verified, covering both pre- and post-`JWT-AUDIT`
encryption schemes:

| Round-trip | Path | Asserts |
|---|---|---|
| `check_4a` | `derive_sol` → `encrypt_for_storage` (v0 / JWT_SECRET-keyed) → `decrypt_with_version` | recovered key bytes match exactly |
| `check_4b` | `derive_sol` → `encrypt_for_storage` (v1 / WALLET_ENCRYPTION_KEY-keyed) → `decrypt_with_version` | recovered key bytes match exactly |
| `check_4c` | `derive_sol` → encrypt v0 → `reencrypt_v0_to_v1` → decrypt at v1 | post-migration ciphertext recovers original key |

Crucially, `check_4c` exercises the migration path that the
`reencrypt_wallets` binary will run during the JWT_SECRET-decoupling
cutover. Wallets created today (v0) survive the cutover and are
readable post-cutover under v1. The recovered hex re-parses as a valid
32-byte ed25519 secret seed, confirming we can sign with it
post-decrypt.

> Note: The design doc (§6.4) describes this as "encrypt → decrypt → sign
> a transaction → broadcast". The first three steps are covered above.
> The fourth (broadcast) is implicitly covered by check 1, which signs
> with a key the test itself generated and decrypted from the env-var
> hex — same code path.

**Implication:** the dual-key encryption scheme correctly handles
Solana keypairs; no Solana-specific encryption work is needed.

## Check 5 — Decimal correctness (SOL = 9, USDT-SPL / USDC = 6)

**Status:** **PASS**.

Pinned to assertions:

- 10⁹ lamports = 1 SOL exactly (`escrow_balance.rs:148` divisor).
- 10⁶ minor units = 1 USDC / USDT exactly.

Mint decimals were cross-verified against mainnet
`getTokenSupply` during this audit:

| Mint | Address | Decimals |
|---|---|---|
| USDC | `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` | 6 |
| USDT | `Es9vMFrzaCERmJfrF4H2FYD4KCoNkY11McCe8BenwNYB` | 6 |

The test pins the conversion constants directly so any refactor that
drifts them (e.g. someone "improving" `lamports as f64 / 1e9` to
something subtly wrong) breaks the build.

**Implication:** TKT-214.2's `USDT_SPL_MINT` constant should use the
mainnet USDT mint pinned above. No conversion-factor changes needed.

### Resolving the design doc's "communication failure" suspicion

The design doc (§10, open question 1) flagged: _"Who wrote
`services/blockchain/solana.rs`? Investigate whether it's
production-grade or scaffolding the original author would push back on.
Communication failure on the team is a yellow flag worth
investigating."_

The communication failure is real but its resolution is benign: the
original author **is JP**, who is also the recipient of this report.
There is no missing third party. The implementation was commissioned to
a known scope (STORY-02), shipped with 15 unit tests, and hardened via
an explicit follow-up. Marcello (author of the design doc) had simply
not been involved in STORY-02 and discovered the code during his
investigation — hence the "discovered, not commissioned" framing in
§3.2 of the design doc.

**JP's stance on production-readiness is the open ask** — but the audit
trail (intentional commit, unit tests from day one, on-chain
confirmation hardening added based on real-world feedback) is
inconsistent with "scaffolding I wouldn't push back on shipping".

## Bugs / gaps found during the audit

None that block TKT-214.2.

The following minor cosmetic / future-work items were noted but **out
of scope** for this verification ticket:

1. **`pub const USDC_MINT` is the only mint constant.** TKT-214.2 will
   add `USDT_SPL_MINT`; this is expected and on-plan.
2. **`confirm_solana_tx` is only called from `send_spl_token`** (line
   526), not from `send_sol` (line 398). For native SOL transfers the
   code returns the signature without verifying on-chain confirmation.
   This is _probably_ fine because native SOL transfers can't fail
   post-preflight in the same way SPL transfers can (no ATA-creation
   race), but it's worth a follow-up ticket to verify the assumption
   and either backfill `confirm_solana_tx` on `send_sol` or document
   the asymmetry.
3. **`SOL_RPC_URL` defaults to `api.mainnet-beta.solana.com`** — the
   public, rate-limited, unreliable endpoint. TKT-214.3 (Helius
   migration) addresses this.
4. **No `USDT_SPL_MINT` cross-check against Tether's official source.**
   The mint pinned in the test (`Es9vMFrz…`) matches what the design
   doc lists in §8.2 and what `getTokenSupply` returns for Tether's
   canonical SPL mint, but `TKT-214.2` should still cite Tether's
   official documentation in the code comment alongside the constant
   so a future reader can re-verify without a chain query.
