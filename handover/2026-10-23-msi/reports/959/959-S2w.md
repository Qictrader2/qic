## What changed
1. The start mints one key (`crypto.randomUUID()`) at confirm and keeps it in the query-cache commit record, so it outlives the hook instance like the step. Start again resends the stored body under the stored key. `reset` (known answers only) drops the key. This matches the 920 hook: the key is kept while the answer is unknown and released after an answer.
2. Check status for a start reads `GET /money-requests/{key}`:
   - `completed` (with `trade_start`, a trade and an id) means found. The trade is read once for its status.
   - `refused` (with `trade_start`) runs through the start classifier and keeps the shortfall figures.
   - `not_received` follows the existing in-flight and timeout rule.
   - `processing` stays unconfirmed.
   - `failed` means "did not start" and logs a warning (only withdrawals write it).
   - An unreadable body or another key's answer is a failed read (offline).
   - The trades-list scan is deleted.
3. The start reference is `requestReferenceFromKey("T", key)`. An error is logged if a key ever has fewer than 8 hex digits.
4. Status and error codes:
   - 429 is definite for every action (it agrees with the hook), with a new start `rateLimited` copy.
   - 409 `idempotency_key_reused` and `operation_in_progress` stay unconfirmed.
   - `KYC_REQUIRED` and `SOLANA_NOT_ENABLED` are read by code.
   - Stale comments are fixed.
5. Retries the boards draw:
   - Start again appears on A21a seller, C6 frame 28 and C22b frames 41 and 42, with the full line "To trade, start again. You'll see the price again before you confirm." and C6's caption.
   - The in-room Try again frames (A21a, A21b, A22a, A22b) already matched; A22c and A22d draw none.

## Consumer contract for 957-S7
- A start's `send(payload, idempotencyKey)` must put the key in the body: `tradesApi.createTrade({...payload, idempotencyKey})`, or `useCreateTrade().mutateAsync({...payload, idempotencyKey})`.
- `StartOutcomeBody` `onRetry` must reopen "Start this trade?" at the current price with the amount locked. That confirm's primary calls `retry()`.
- Build the success screen from the returned trade, because a late first request comes back priced when it ran.

## Backend-blocked items
- **920 follow-up (no card yet):** only the trade start is keyed. Mark paid, release, cancel and dispute take no key and the lookup can't see them. So the in-room actions:
  - send no key;
  - keep the trade-read Check status;
  - show a display-only reference that support can't look up.
- **920 follow-up:** `create_trade_request` runs the KYC extractor and `offer::find_by_id` before `k.replay`. If a late first start lands and then the offer 404s or KYC lapses, Start again gets a refusal while the first trade exists. The window is narrow.
- **Known limit, frontend:** the commit record lives in the tab's query cache. After a reload, a new tab or a forced logout, a fresh start mints a new key, so a late first request could still open a second trade.
