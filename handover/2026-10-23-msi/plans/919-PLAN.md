# Ticket 919: Withdrawals: customers cannot see that a withdrawal is held

Severity: logic
Track: FULL
Size: L
Budget: 300 min
CI allowance: 45 min
Size table: 2026-10-16
Risk areas: none
Frontend: True

## Expected behaviour
Sources: the card's Expected behaviour section, AC1 to AC3 and their mandatory QA coverage, and the owner decision comment of 22 Oct 2026, which makes the approved v5.2 boards B8a to B8d and the BE1 note on B19 the design gate and the exact wording. Christian confirmed that wording on 21 Oct 2026. The boards were read from ~/Downloads/906-design-pack-v5.2/ (B8a, B8b, B8c, B8d, B19).

1. While a withdrawal is held by HARC, every customer transaction response for it carries `customerOutcome: "held"`. Status stays 'pending'. This is derived from backend hold state, never from elapsed time (B8d table: 'Pending + hold_reason' maps to 'Taking longer than usual'; B19 item 8). The app labels the row exactly "Taking longer than usual" and shows the withdrawal reference and the link "Get help with this withdrawal" to /report?withdrawal=<reference> (B19 item 8, BE1). Where the layout shows a helper line, the board's held sentence is the only allowed copy: "Your {amount} {currency} stays held and you don't need to do anything. If it can't be sent, we'll cancel it and restore your balance." (B8a held card).
   Worked example: QA buyer withdraws 200.00 USDT on Tron with a 2.50 fee, and the treasury cannot cover it. GET /wallet/transactions returns that row with status 'pending' and customerOutcome 'held'. /wallet shows "Taking longer than usual", the reference, and "Get help with this withdrawal". Available balance stays reduced by 202.50.
2. When the hold resolves by resume, the row turns 'confirmed', `customerOutcome` turns null, and the app shows the normal confirmed status. No held label and no help line remain.
3. When the hold resolves by cancel (timeout auto-cancel, admin cancel, or a proven-unlandable settle), the row turns 'failed' with a refund. `customerOutcome` is 'cancelled' and `refund` is present. The app shows exactly "Cancelled, balance restored" only when the backend has confirmed the funds are back, meaning the refund entry is present (owner decision point 2). The reference and help link stay on that row (BE1). The balance is back by amount plus fee, once.
   Worked example: the 200.00 USDT hold above times out after WITHDRAWAL_PENDING_TIMEOUT. The row shows "Cancelled, balance restored" with the existing 818 refund line "Refunded 202.5 USDT to your balance (includes the 2.5 USDT fee)." Available rises by 202.50.
4. A failed withdrawal without refund evidence never claims the balance is restored. It keeps the current "Cancelled" label. The words "Failed" and "Rejected" never reach the customer (B8a header, B8d). The history status filter chip that reads 'failed' is labelled "Cancelled"; its query value stays 'failed' (BE1).
5. A possibly-broadcast hold (hold_reason 'broadcast_failure') is not timer-cancelled. It keeps showing "Taking longer than usual" until chain proof or an admin reconcile settles it as Sent or as cancelled with a refund.
6. The customer never sees an internal reason. No hold_reason, failure_reason, needs_asset, treasury balance, metadata, claim or admin detail appears in any customer response or screen. The outcome value is the single word 'held', never reason-specific (AC3).
7. Held, failed and unknown stay distinct (owner decision point 2, B8d 'three different answers'). 'held' is a backend outcome on an accepted withdrawal. 'Failed, refused' is a synchronous 4xx that never creates a row. 'Unknown/unconfirmed' is client-side only, and card 920 owns its Check status flow. This card adds no new copy for refused or unknown outcomes.

## Diagnosis
Implementation gap, verified by reading the source snapshot (backend 8fda17fa, frontend a73d2708). It was not reproduced on a running environment.

1. Backend state exists but is never exposed to the customer. A HARC-held withdrawal is a `wallet_transactions` row with tx_type 'withdrawal' and status 'pending', plus at least one of: `metadata.hold_reason` set ('insufficient_treasury' from `create_treasury_topup_hold`, qictrader-backend-rs/src/services/withdrawal.rs:2031-2050 and 2147-2168; 'reserve_floor' or 'broadcast_failure' from `hold_pending_pooled`, src/services/treasury_pooled_send.rs:1193-1237; 'broadcast_failure' from `park_uncertain_send`, withdrawal.rs:3540; 'kms_unavailable' per docs/intended-entity-state-machines.md:689), or `failure_reason` set by the legacy broadcast-failure hold `hold_pending_and_notify` (withdrawal.rs:281-346). The admin exception queue already uses this exact predicate (src/repo/admin_exception.rs:78-84: pending AND (failure_reason IS NOT NULL OR metadata->>'hold_reason' IS NOT NULL)).
2. The customer contract carries no hold signal. `TransactionResponse` (src/api/wallet.rs:214-264) exposes status, hash, amounts, `customerOutcome` and `refund`, but not metadata or failure_reason. `WithdrawalCustomerOutcome` has only `Cancelled` (wallet.rs:199-203), and `withdrawal_customer_outcome` (wallet.rs:272-291) returns None for every pending row. A unit test even pins a held pending row to `customerOutcome: null` (wallet.rs:5136-5142). GET /wallet/transactions (`get_transactions`, wallet.rs:1305) and GET /wallet/pending (`get_pending_transactions`, wallet.rs:1423) both go through `rows_to_responses` -> `tx_to_response`, so a held withdrawal is indistinguishable from an ordinary in-flight one.
3. The frontend has nothing to show from. `wallet-api.ts:245` maps only `customerOutcome === "cancelled"`; `transaction-display.ts:71-82` `statusLabel` returns the raw status ('pending') for a held withdrawal and plain "Cancelled" for any failed withdrawal, whether or not the backend has confirmed a refund. The status filter chip shows the raw value 'failed' (TransactionHistory.tsx:91, 272-282). No surface shows a withdrawal reference or a help link, and /report (frontend/src/app/(main)/report/page.tsx) ignores query parameters.
4. Resolution paths already clear the backend state, so a derived flag stays correct without new writes. Resume finalize sets status 'confirmed' and either restamps hold_reason to 'resumed_after_topup' or removes it (withdrawal.rs:3925-3946). Settle-as-not-sent removes hold_reason (withdrawal.rs:5853-5861). Timeout auto-cancel (`auto_reject_timed_out`, withdrawal.rs:356; selected in jobs.rs:1697-1714 by failure_reason IS NOT NULL and not broadcast_failure) and the 818 admin cancel flip the row to 'failed' with a compensating Refund ledger entry, which the history query already returns as `refund` (wallet.rs:1411-1418).

Root cause: verified from source. The missing piece is a derived, customer-safe outcome value and the frontend labels that read it. Not verified: live staging behaviour of a real hold, which needs the QA run in acceptance.

## Scope
Included, backend (qictrader-backend-rs):
1. Add a `Held` variant to `WithdrawalCustomerOutcome` (serialized 'held'). Derive it in `withdrawal_customer_outcome` for tx_type 'withdrawal' + status Pending + (failure_reason present OR metadata.hold_reason present and not 'resumed_after_topup'). This is the same predicate as the admin exception queue. No new columns, no migration, no change to any write path, job, guard or transition.
2. GET /wallet/transactions and GET /wallet/pending pick it up through `tx_to_response`. The POST /wallet/withdraw response also goes through `tx_to_response`. It may or may not show 'held', depending on whether the hold was stamped before the response row was read; the history endpoints are the contract.
3. Unit tests for the derivation matrix, plus a DB-backed HTTP contract test on /api/v1/wallet/transactions and /api/v1/wallet/pending, extending the harness in tests/wallet_withdrawal.rs:1289.
4. Docs: HARC.md (user-facing presentation of the Hold beat) and the withdrawal section of docs/intended-entity-state-machines.md, saying customers see a derived 'held' outcome.

Included, frontend (minimal current-app change, owner decision point 3b):
5. Types and mapper accept 'held' (wallet.types.ts:156, wallet-api.ts:245, profile-transactions.ts:48).
6. `statusLabel`: held -> "Taking longer than usual"; customerOutcome 'cancelled' with refundedAmount present -> "Cancelled, balance restored"; other failed withdrawals stay "Cancelled". Add a reference helper and a help-link href helper in transaction-display.ts, so the table, mobile cards, CSV export and profile panel cannot drift.
7. TransactionHistory.tsx: show the held and cancelled labels with a non-spinning status style for held, the reference and the "Get help with this withdrawal" link on held and cancelled withdrawal rows (mobile cards and desktop table), and rename the 'failed' chip label to "Cancelled".
8. components/profile/TransactionHistory.tsx: status styles for the two new labels, with reference and link where the row layout allows.
9. /report page: read the `withdrawal` query parameter and prefill the reference into the existing form, adding no new copy, so the help link carries the reference to support.
10. Unit and regression tests for labels, mapper, export and profile parity, plus the design package (annotated current layout; required by the contract for any frontend change).

Excluded:
- Any change to HARC write paths, timeout, resume, reconcile, refund or admin cancel behaviour.
- New admin surfaces.
- The redesign's withdrawal outcome dialog, the 'Sending'/'Sent' relabel and the Check status / unconfirmed flow (cards 906 and 920).
- The post-submit toast in WithdrawModal.
- Notifications and emails (the existing "Withdrawal Processing" notification is unchanged).
- Deposit sweep holds (859 already shows "On hold").
- Custodial /custodial-wallet history (its separate TransactionResponse, src/api/custodial_wallet.rs:696-744, carries no outcome; the manage page merges it only for on-chain rows that have hashes).
- Adding polling to the transactions query.

Dependencies and rollout:
- Backend first. The frontend tolerates an older backend: a missing customerOutcome maps to null and the row shows today's label.
- The reference format must be the one card 920 will use for the same withdrawal; see preparation_tasks.
- USDT-only monitoring scope applies: holds exist only for Tron and Solana USDT pooled sends, and QA uses USDT.

## Implementation
1. qictrader-backend-rs/src/api/wallet.rs:199-203: add `Held` to `WithdrawalCustomerOutcome` (snake_case serializes to "held"). Keep `Cancelled` unchanged so 818 consumers keep working.
2. wallet.rs:272-291 `withdrawal_customer_outcome`: before the Failed branch, return `Some(Held)` when tx_type == "withdrawal" && status == Pending && (tx.failure_reason.is_some() || hold_reason(metadata) is Some(r) with r != "resumed_after_topup"). Read hold_reason as a string only; never copy it into the response. Put the predicate in one small pure fn (e.g. `is_harc_held`) with a doc comment pointing at repo/admin_exception.rs:78-84, so the customer and admin views of 'held' cannot diverge. Use no timestamps, so status is never inferred from elapsed time.
3. wallet.rs tests module (around 5066-5142): replace `customer_outcome_none_for_pending_withdrawal` and the held-row null assertion at 5136-5142 with a matrix: insufficient_treasury, reserve_floor, broadcast_failure, kms_unavailable, failure_reason-only -> held; pending with neither -> None; pending with processing=true and hold_reason -> held; confirmed with resumed_after_topup -> None; failed with refund -> cancelled; deposit/transfer pending with a failure_reason -> None. Add a serialization test: a held row's JSON has customerOutcome "held", and its key set equals the existing TransactionResponse key set (no metadata, holdReason or failureReason keys), with no substring of the row's failure_reason anywhere in the serialized body.
4. qictrader-backend-rs/tests/wallet_withdrawal.rs (reuse make_token/create_user/create_wallet and the GET harness at ~1289) or a new tests/withdrawal_held_outcome_919.rs: seed a USDT Tron withdrawal row through `create_treasury_topup_hold` (or direct insert matching topup_hold_metadata), GET /api/v1/wallet/transactions and /api/v1/wallet/pending as the owner and assert customerOutcome 'held' plus no leaked fields. Then (a) mark it confirmed the way finalize does (status confirmed, hold_reason resumed_after_topup) and assert null; (b) on a second row call `services::withdrawal::auto_reject_timed_out` (or the 818 admin cancel core) and assert status failed, customerOutcome 'cancelled', refund.amountMinor = amount + fee, and wallet balance restored exactly once. Add a 'broadcast_failure' row older than the timeout: run `jobs::run_withdrawal_timeout_monitor` or assert the stale query excludes it, and check it still reads 'held'.
5. Docs: qictrader-backend-rs/docs/design/patterns/HARC.md (Hold beat and rule 1: customers see a derived `customerOutcome: "held"`, labelled "Taking longer than usual"; never a reason) and docs/intended-entity-state-machines.md:594-599 (same sentence, no new state). Run the design-check binary if it covers these docs (src/bin/design_check.rs).

## Risks
- The customer money status is derived from hold state. If the predicate drifts from the backend's real hold shapes, a held withdrawal reads as normal or a normal one reads as held. Mitigation: one pure predicate mirroring repo/admin_exception.rs:78-84, plus a matrix test over every hold_reason value in HARC.md and intended-entity-state-machines.md (including kms_unavailable and the legacy failure_reason-only shape).
- AC3 information disclosure: the hold reason and failure_reason contain internal treasury and RPC detail. The response must not gain metadata or reason fields. The serialization test asserts an exact key set and no failure_reason substring.
- "Cancelled, balance restored" is a statement about money. It must show only when the refund entry is present, never from the status or markers alone; the marker-only 818 cancel shapes keep "Cancelled".
- A 739-style orphan (pending with neither hold_reason nor failure_reason) and the stale-pending backstop alert stay 'pending', not held. This is intentional (backend state, never elapsed time), but the customer sees the ordinary pending label until the reclaim pass resolves it.
- The transactions query has no refetch interval (use-wallet.ts:135-152), so the transition from held to sent or cancelled shows on the next fetch, not live. Acceptable for this card; QA must reload.
- Renaming the 'failed' filter chip to "Cancelled" also covers failed deposits and transfers. That follows BE1, but check the export and filter tests.
- Withdrawal reference format: if this card derives it from the transaction id and card 920 derives the 'request reference' from the idempotency key, one withdrawal could show two references. The format must be agreed before the frontend build (see preparation_tasks).
- Changing 818 cancelled-label tests touches shipped behaviour; regression tests for profile/manage/export parity must be updated, not deleted.
- Staging QA needs a real HARC hold. Producing one on shared staging (treasury shortage or a seeded held row) must follow the staging fixture practice and be cleaned up. Prod observation is separate release work.

## Acceptance and evidence

### AC1: A customer can see when their withdrawal is being held.
- Setup: DB-backed contract test: a USDT Tron withdrawal parked by create_treasury_topup_hold (status pending, metadata.hold_reason 'insufficient_treasury', failure_reason set) for a test user; the owner calls GET /api/v1/wallet/transactions and GET /api/v1/wallet/pending.
  Expected: Both responses contain the row with status 'pending' and customerOutcome 'held'.
  Evidence: New sqlx test in tests/wallet_withdrawal.rs (or tests/withdrawal_held_outcome_919.rs), passing in backend CI on Postgres; cite the CI log line.
- Setup: Unit matrix on withdrawal_customer_outcome / tx_to_response: pending withdrawals with hold_reason 'reserve_floor', 'broadcast_failure', 'kms_unavailable', with processing=true, and with failure_reason only (legacy hold_pending_and_notify shape).
  Expected: Every case serializes customerOutcome "held".
  Evidence: cargo unit tests in src/api/wallet.rs tests module, run in backend CI.
- Setup: Unit test: an ordinary pending withdrawal with neither hold_reason nor failure_reason, created_at older than WITHDRAWAL_PENDING_TIMEOUT.
  Expected: customerOutcome is null: the held state is never inferred from elapsed time.
  Evidence: cargo unit test in src/api/wallet.rs, backend CI.
- Setup: Frontend unit/regression tests: a WalletTransaction with type 'withdrawal', status 'pending', customerOutcome 'held', rendered by TransactionHistory (mobile and desktop), by buildProfileTransactions, and by the CSV export.
  Expected: Label is exactly "Taking longer than usual", with no spinner. The withdrawal reference and a link "Get help with this withdrawal" to /report?withdrawal=<reference> are visible and keyboard-focusable. The CSV status column reads "Taking longer than usual".
  Evidence: bun tests transaction-display-919-held.test.ts plus the updated 818 profile/manage/export regression tests, run locally on the touched files and in the frontend gate.
- Setup: Staging, QA buyer account (USDT only): produce a real HARC hold on a Tron USDT withdrawal (principal above the staging hot-pool balance, or a seeded held row tagged for cleanup per staging fixture practice), then open /wallet and /wallet/manage/USDT at 390, 768 and 1440 widths, and /profile.
  Expected: GET /wallet/transactions shows customerOutcome 'held' for that withdrawal. Every surface shows "Taking longer than usual", the reference and the help link; the link opens /report with the reference prefilled. Available balance stays reduced by amount plus fee.
  Evidence: Staging QA recording and screenshots by the qic-qa-signin flow, plus the captured network response for /wallet/transactions.

### AC2: The held state clears when the withdrawal resumes or is cancelled, with the balance restored on cancel.
- Setup: Contract test: the held row from AC1 is resumed the way finalize writes it (status confirmed, tx_hash set, hold_reason 'resumed_after_topup'); a second held row is finalized by the original-sender path (hold_reason removed).
  Expected: GET /wallet/transactions returns customerOutcome null and status 'confirmed' for both, and the frontend shows the normal confirmed status with no held label, reference or help line.
  Evidence: sqlx contract test in backend CI and a frontend label unit test for a confirmed withdrawal.
- Setup: Contract test: a held insufficient_treasury row past the timeout is cancelled by services::withdrawal::auto_reject_timed_out. The test records the wallet balance before and after.
  Expected: Status 'failed', customerOutcome 'cancelled', refund.amountMinor equals amount plus fee, and wallet balance rises by exactly amount plus fee, once (a second auto_reject call changes nothing). The frontend label for this row is "Cancelled, balance restored".
  Evidence: sqlx test in backend CI, plus frontend unit test of statusLabel with customerOutcome 'cancelled' and refundedAmount set.
- Setup: 818 admin cancel of a held row (POST admin cancel core) and a 'broadcast_failure' held row older than the timeout with the withdrawal monitor run.
  Expected: The admin-cancelled row reads cancelled with refund, as above. The broadcast_failure row is not timer-cancelled and still reads customerOutcome 'held'.
  Evidence: sqlx tests in backend CI (extend the existing 818 cancel test fixtures or the new 919 test file).
- Setup: Frontend unit test: a failed withdrawal with customerOutcome null or 'cancelled' but no refundedAmount (marker-only legacy shape).
  Expected: Label is "Cancelled", never "Cancelled, balance restored" and never "Failed". The status filter chip for 'failed' reads "Cancelled" and still requests status=failed.
  Evidence: bun unit tests on transaction-display.ts and TransactionHistory filter chips.
- Setup: Staging, QA buyer: let the held withdrawal from AC1 auto-cancel (WITHDRAWAL_PENDING_TIMEOUT_SECS override if already configured on staging, otherwise the 1h window), or resume it by topping up the staging hot pool; reload /wallet.
  Expected: Resumed: the row shows the normal confirmed status with a hash. Cancelled: the row shows "Cancelled, balance restored" with the refund line, reference and help link, and Available is back by amount plus fee.
  Evidence: Staging QA screenshots of before and after, balance readback via GET /wallet/balance, and the network response for /wallet/transactions.

### AC3: No internal reason is shown to the customer.
- Setup: Serialization unit test and contract test on a held row whose failure_reason holds a distinctive marker string (e.g. 'pooled send held (reserve_floor): RPC-SECRET-919') and whose metadata holds needs_asset/treasury_balance_minor.

No key named holdReason, hold_reason, failureReason, failure_reason, metadata, needsAsset or treasuryBalanceMinor appears, the marker string appears nowhere in the body, and customerOutcome is exactly 'held' for every hold_reason value.

- Setup: Frontend test rendering a held and a cancelled withdrawal in TransactionHistory and the profile panel.
  Expected: Only board wording appears ("Taking longer than usual", "Cancelled, balance restored", the reference, "Get help with this withdrawal", and the existing refund line). No hold reason, error text or admin wording is rendered.
  Evidence: bun component tests asserting the rendered text.
- Setup: Staging QA: inspect the /wallet/transactions and /wallet/pending network responses and the /report prefill for the held withdrawal.
