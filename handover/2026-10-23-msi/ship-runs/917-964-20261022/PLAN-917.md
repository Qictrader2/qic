# Ticket 917: Passwords: reset and change accept shorter passwords than sign-up

Severity: security
Track: FULL
Size: L
Budget: 300 min
CI allowance: 45 min
Size table: 2026-10-16
Risk areas: authorization
Frontend: True

## Expected behaviour
Source: the owner decision of 13 Oct 2026 quoted in the card ("sign-up, password reset and change-password all require at least 12 characters"), the card's Expected behaviour section and the four ACs. 1) Reset (/reset-password?token=...): a customer who enters an 11-character new password and a matching confirmation sees the in-page error "Password must be at least 12 characters" before any request is sent. A forged or direct POST /api/v1/auth/reset-password with an 11-character newPassword returns 400 VALIDATION_ERROR with message "password must be at least 12 characters". The reset token is not consumed by that refusal, so a retry with a 12-character password and the same token returns 200 "password reset successfully — please log in with your new password". 2) Change-password (Settings > Security > Change Password): new passwords of 8, 9, 10 and 11 characters are refused in the page with "Password must be at least 12 characters". The same requests sent directly to POST /api/v1/users/password/change return 400 with "password must be at least 12 characters". A 12-character password with the correct current password returns 200 "password changed successfully". The page's existing uppercase/lowercase/number checks stay as they are, so the browser example is "Abcdefghij12". 3) Message parity: on both pages the browser text and the server text name the same minimum, 12, worded as in sign-up's server message ("password must be at least 12 characters"; the page capitalises the first letter). The reset page's native `minLength` tooltip must not pre-empt that message. The helper text and placeholder say 12. 4) Existing accounts: a customer whose stored password is 8 characters (for example "Abcdef12") signs in exactly as before. They see no forced reset, no warning and no extra step, and the 12-character rule applies only when they next set a password. 5) Security invariants: an incorrect current password still returns 401 "current password is incorrect" (users.rs:1605-1606). Invalid, expired or used reset tokens still return "invalid or expired reset token". The one-hour expiry, single use, session revocation (all sessions on reset, other sessions on change) and the password-changed notification are unchanged.

## Diagnosis
Verified by reading source at backend pin f043a141 and frontend pin 1ac41624. This is a read-only diagnosis: no request was sent to staging or local. (1) Sign-up: `SignupRequest.password` has `#[validate(length(min = 12, message = "password must be at least 12 characters"))]` (qictrader-backend-rs/src/api/auth.rs:63; the card says :62). That length rule is the only server-side password rule for sign-up; `signup` (auth.rs ~430-540) adds no composition or maximum check. (2) Reset: `ResetPasswordRequest.new_password` has `length(min = 6, message = "password must be at least 6 characters")` (auth.rs:138; the card says :121). `reset_password` (auth.rs:2805) extracts through `ValidatedJson`, so validation runs before the token lookup `find_valid_reset_token` (repo/user.rs:1668). The reset page checks `newPassword.length < 6` with the message "Password must be at least 6 characters" (frontend/src/app/(auth)/reset-password/page.tsx:57-58). The placeholder says "min 6 characters" (:135), and both inputs carry `minLength={6}` (:140, :157). (3) Change-password: `ChangePasswordRequest.new_password` has `#[validate(length(min = 8))]` with no message (qictrader-backend-rs/src/api/users.rs:144; the card says :138). `format_validation_errors` (src/extractors/validated.rs:47-60) therefore returns the generic text "new_password: validation failed (length)" with no minimum, so AC3 also needs a message, not just a number change. `ChangePasswordSection.tsx:35` refuses passwords under 8 characters with "Password must be at least 8 characters". The helper text at :187 reads "Min 8 characters with uppercase, lowercase, and number", and the strength meter starts scoring at 8 characters (:46). (4) Tests: tests/ has no test for /auth/reset-password. The only change-password test (tests/jwt_audit_2026_05_revocation.rs:304) uses a 28-character password and is unaffected. (5) Existing short passwords: `LoginRequest.password` is `length(min = 1)` (auth.rs:88), and login only calls `verify_password` against the stored hash (auth.rs:965-970). Sign-in has no length or policy gate, so AC4 holds today and must stay that way. (6) Unused constant: `PASSWORD_MIN_LENGTH = 8` in frontend/src/lib/constants.ts:106 is referenced nowhere. Root cause: sign-up was raised to 12 (EML-003), but the reset and change-password validators and their pages were never updated with it. Not reproduced live. The read-only role forbids shared-environment calls, so the staging proof is part of QA.

## Scope
Included: (a) backend validators for ResetPasswordRequest.new_password (auth.rs:138) and ChangePasswordRequest.new_password (users.rs:144), both raised to min 12 with sign-up's exact message; (b) a backend test file covering 11/12 on both endpoints, token survival after a refused reset, unchanged current-password and token rules, and sign-in with an existing 8-character password; (c) frontend reset page validation, placeholder and native minLength attributes; (d) ChangePasswordSection length check, helper text and strength-meter length thresholds; (e) frontend unit tests for both components; (f) optionally setting the unused frontend PASSWORD_MIN_LENGTH constant to 12 and using it on these two pages only. Excluded: sign-up behaviour and the sign-up page's client-only symbol/composition checklist. No new composition rules on either server endpoint, because sign-up's server validator has none and the owner decision is about length only. Login, 2FA, account deletion and OAuth password-less accounts are unchanged. Forced reset or any migration of existing hashes is excluded (AC4 forbids it). The admin create-user validator (`AdminCreateUserRequest.password`, admin.rs:3639, min 8) is staff-only, not a customer path, and the owner decision does not name it. It stays out of scope, and the report should suggest a separate /newticket. Test-account seeding (services/test_accounts.rs, admin.rs:7702) is excluded. Card 906 redesign: this card corrects only rules and copy on the current pages. If 906 later rebuilds these screens, the 12-character rule and message carry forward. Dependencies: none. Rollout: backend and frontend can ship in either order. Backend first is safer; frontend first only makes the browser stricter than the server for a short window. No migration, no config, no feature flag, and the change is reversible.

## Risks
- Authentication rule change: the accepted minimum for newly set passwords on POST /api/v1/auth/reset-password and POST /api/v1/users/password/change rises from 6 and 8 to 12. Any client or script that sets shorter passwords, including QA helpers that rotate QA account passwords, will now get 400.
- Security invariants must not move: current-password verification (users.rs:1605), reset-token validity/expiry/single-use (repo/user.rs:1668), and session revocation on reset and change are untouched. Tests assert each one so a refactor cannot loosen them silently.
- A refused reset must not consume the token. Validation runs in the ValidatedJson extractor before token lookup today, and the new integration test pins that order so a future handler rewrite does not burn the customer's one-hour link on a short password.
- Character counting can differ: the validator crate counts Unicode characters, while JavaScript `.length` counts UTF-16 code units, so astral characters (emoji) count 2 in the browser and 1 on the server. A password of 6 emoji passes the browser check but the server refuses it with the same 12-character message. The only effect is a server message instead of an in-page one, and the backend unit test pins character counting.
- AC4 regression risk: no change may add a length or policy check to login, 2FA, account deletion or session refresh. Existing short passwords keep working and no forced reset is introduced.
- Policy gap left open: AdminCreateUserRequest (admin.rs:3639) still allows 8-character passwords for staff-created accounts. That is out of scope here and needs its own card.
- Card 906 overlap: the 906 redesign may rebuild the reset and settings screens. If it lands later, its implementation must keep the 12-character rule and message.
